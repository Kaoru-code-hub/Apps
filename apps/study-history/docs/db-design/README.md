## 設計方針

### 1. ストレージ
- **IndexedDB** をブラウザ内ストレージとして利用
- ラッパーライブラリとして **Dexie.js** の利用を想定（スキーマ定義・マイグレーション・複合インデックスが扱いやすい）
- 本ドキュメントでは IndexedDB の「オブジェクトストア」を便宜的に **テーブル** と呼称する

### 2. 命名規則
- テーブル名：複数形・スネークケース（例：`study_records`）
- カラム名：スネークケース（例：`started_at`）
- 主キー：`id`（自動採番の整数 / `++id` 相当）
- 日時：UNIX エポックミリ秒（`number`）で保持。表示時に Asia/Tokyo に変換

### 3. 時間の単位
- **内部はすべて「分」または「ミリ秒」で統一**
  - 計測時間（`duration_minutes`）：**分**
  - 開始／終了時刻（`started_at` / `ended_at`）：**ミリ秒（UNIX epoch）**
  - 目標時間（`target_minutes`）：**分**（UI では時間単位で入力 → 分に変換して保存）

### 4. 多対多の表現
- 1 記録に複数カテゴリ付与可（要件 §2）
- 中間テーブル `study_record_categories` で多対多を表現

### 5. 削除方針
- カテゴリ削除時の挙動は要件未確定（要件 §10 検討項目）
- 暫定で **論理削除**（`deleted_at` カラム）を採用
  - 物理削除すると過去記録の集計表示が壊れるリスクがあるため
  - 確定後に物理削除に切り替えるのは容易だが逆は困難

### 6. インデックス戦略
- ダッシュボード集計 200ms 以内を満たすため、`started_at` を必ずインデックス化
- カテゴリ別集計のため、中間テーブルに複合インデックスを設定

### 7. バージョニング
- IndexedDB のスキーマバージョンを `1` から開始
- カラム追加・スキーマ変更時はバージョンを上げ、Dexie のマイグレーションで対応
